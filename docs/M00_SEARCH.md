# M00 — Search & grounded LLM

Status: approved (D26; pipeline revised D28) · Updated: 2026-10-07 · Serves: M02, M04, M07, M11 · Sources: S24, S47, S54, S56

## Purpose
Search whole filings and news; let an LLM work only on retrieved, stored passages, with every claim mechanically checked.

## No text limits (D22)
Documents are stored and indexed whole; character limits exist only for display. The old code cut analysis text in 13 places (e.g. first 20k + last 60k chars per filing; 14k chars of LLM input).

## Tier 1 — market-wide discovery (EDGAR full-text search)
- Which filers mention a phrase, all companies since 2001; hit counts by date window = trend signal (M02).
- Limits: ≤ 10,000 hits per query; no matched text returned (fetch the document); one quoted phrase per query; OR groups unreliable.

## Tier 2 — local deep search (SQLite FTS5 in corpus.db)
- Documents split into sections (10-K Items 1, 1A, 7, 7A, 8; 10-Q parts; 8-K items; exhibits) with character offsets.
- Sections split into paragraph-aligned passages (~1.5–3k chars, offsets into the document); passages are the unit that is ranked and cited. Whole sections stay retrievable (D-SRCH-7).
- FTS5: exact phrases, prefix, boolean, NEAR proximity, column filters, BM25 ranking, snippet/highlight, porter stemming.
- Section text stored once; FTS5 table self-contained if external-content naming would break snippet()/highlight().
- Tier 2 results are the only material the LLM may see.

## Tier 3 — semantic search (later, optional)
Embeddings to catch the same idea in different words for theme spotting. Evaluate after Tier 2 works.

## Grounded pipeline (D21, revised D28)
Python searches and extracts; the LLM runs only when the owner asks, and only on the refined data set.
1. **Search (code):** FTS5 over passages; each has `passage_id`, accession, filename, section, offsets.
2. **Extract (code, versioned parser):** e.g. R19 finds outlook/guidance passages in earnings EX-99.1 and parses metric, period, low/high, unit, GAAP/non-GAAP. Each row points at its sentence by offsets, so provenance is built in. Sentences the parser cannot read go to the review queue with their passage; no LLM parse (D-SRCH-8).
3. **Ledger & scoring (code):** guidance rows stored, later scored against XBRL actuals (R19). Financial numbers come from XBRL or the parser, never the LLM.
4. **Analyze (LLM, on request only):** input = ledger rows + the passages behind them, each with an ID. Output = observations (e.g. trends across releases), each citing IDs with a verbatim quote.
5. **Verify (code):** quote exists in the cited passage (whitespace/quote-normalized); every number and unit in the observation appears in the cited passages or rows ("$1.2 billion" = 1.2e9 on both sides); a failed check rejects the observation.
6. **Store & show:** observations stored with model, prompt version, citations and verification result (D-SRCH-9); labeled as interpretation and always shown with their sources (accession link, section, quoted sentence).
Provenance survives a corpus rebuild: stored citations carry accession, filename, offsets, document sha256 and the quote, not only `passage_id`. Every LLM call logs model, prompt version, tokens and raw response. Prompts are versioned files. Fixture tests use recorded responses; live LLM calls are opt-in.

## LLM provider (D-SRCH-6)
Google Gemini via the `google-genai` SDK; key `GEMINI_API_KEY` in `.env` (owner enters it; Claude never reads it). Default model `gemini-3.1-flash-lite` (stable; $0.25 in / $1.50 out per 1M tokens, paid tier — content not used by Google; checked ai.google.dev 2026-10-08), configurable; switch (e.g. `gemini-3.8-flash`) only if results are insufficient. Every call is owner-initiated; nothing in the nightly job calls the LLM. Code stays provider-agnostic behind one small interface.

## Failure modes
| Risk | Guard |
|---|---|
| LLM invents a fact | Verifier rejects quotes/numbers not in the cited passage |
| Correct quote, wrong reading | Labeled as interpretation; owner review before it drives a signal |
| Section splitter misses a heading | Fall back to whole-document passages; log failures per form |
| Tokenizer splits domain terms ("HBM3E", "10b5-1") | Test queries for domain terms; add trigram index if needed |
| Porter stemming merges words (`customer*` also hits "custom") | Use quoted phrases for exact wording; unstemmed index only if this misleads in practice |
| Guidance parser misreads a sentence (wrong metric, period or basis) | Exact quote and offsets stored on every row; owner sees the sentence beside the numbers; new wording lands in the review queue, not the ledger |
| Fiscal vs calendar labels ("first quarter of 2027" at Micron = fiscal) | Periods kept as the company states them; mapped to dates against XBRL fiscal periods when scoring |
| Ratio guidance on a near-zero base (Intel GAAP tax rate 476% guided, 198.5% actual) | Stored as stated (verified), flagged `not_meaningful` and excluded from scoring and LLM input (D-SRCH-15) |
| Release gives no guidance (given on the call) | `guidance_scan` outcome `none`, shown as "not in release", never as zero |

## Decisions
- D-SRCH-1 (2026-10-06): No character limits on analysis text (owner).
- D-SRCH-2 (2026-10-06): LLM only on curated, stored data; outputs grounded in sourced passages (owner).
- D-SRCH-3 (2026-10-07): Design approved by owner (D26, was P9).
- D-SRCH-5 (2026-10-07): Tier 1 built (`sec/fulltext.py`, D-SEC-14): phrase search with SIC post-filter and yearly/period hit counts stored over time for M02 trends; matched text is read by fetching the document (Tier 2).
- D-SRCH-4 (2026-10-07): Section splitter built (`sec/sections.py`, version items-1). Splits stored text at line-start "Item N" headings, never changing the text. 10-K headings appear in the table of contents and the body: items are taken in order and, for each, the occurrence after the previous item with the longest body wins. 10-Q labels carry the part (item numbers repeat). Sections tile the document: cover, items, signatures. Required items missing (10-K 1/7/8; 10-Q Part I 1/2; 8-K any) → one "whole" section; every outcome and what was missing goes to `split_log`, countable per form. Exhibits: one section starting after SEC's header lines. `resplit()` re-runs on stored text after a splitter change.
- D-SRCH-6 (2026-10-07): LLM provider Google Gemini (default Gemini 3.1 Flash), key `GEMINI_API_KEY` (owner).
- D-SRCH-7 (2026-10-07): Passages = paragraph-aligned chunks within sections; ranking and citations use passages. Resolves the BM25 short-section bias (owner).
- D-SRCH-8 (2026-10-07): Python does search and extraction; the LLM runs only on owner request, on the refined data set, to find trends; every output carries its sources to the user. Unparsed guidance sentences go to the review queue only (owner; D28).
- D-SRCH-9 (2026-10-07): LLM observations are stored with model, prompt version, citations and verification result (owner). First end-to-end consumer: R19 guidance (owner).
- D-SRCH-10 (2026-10-08): Passages built (`search/passages.py`, chunker para-1): lines packed greedily to ≤ 3,000 chars (trailing blank lines may add 1), tiling each section; over-long lines cut at the last sentence end after 1,500 chars, else whitespace, else hard. Built with the sections on ingest; `ensure_passages()` backfills stored documents. `search/query.py`: FTS5 query over `passage_fts` with cik / doc type / section / accession filters, BM25 with the label column (section label + title) weighted 10:1, `[` `]` snippets; `phrase()` quotes free text (needed for 10b5-1, HBM3E, $ amounts); bad syntax raises `QueryError`. `get_passage()` returns text plus accession, filename, offsets, document sha256 and parser version for citations. Live check: `scripts/search_check.py` (2026-10-08: 134 docs → 4,433 passages in 0.9 s; queries < 10 ms; Item 1A now first for "risk factors"; 10b5-1/HBM3E match as phrases). Guidance samples for the R19 parser: `scripts/guidance_samples.py`.
- Call guidance (M02 D-M02-22, 2026-10-09): the ledger also holds rows from earnings-call transcripts (origin `call`, grade B, A when a company document states the same figure) and owner-downloaded IR PDFs (origin `ir`, A), direction-only rows (no figure), and the capex "including/excluding" clause; transcripts are corpus documents (accession `AV-…`, one section per speaker turn) and appear in search with a source label. Parser guidance-5.
- Use case `call_guidance_check` (M02 D-M02-24, 2026-10-09; owner-triggered, cost first): Gemini lists the forward statements in one call's management turns with exact quotes; verified quotes the code did not store become review items. Never stored as guidance; it only points the owner at sentences, and answers become accuracy labels.
- D-SRCH-11 (2026-10-08): R19 guidance parser built (`guidance/parse.py`, guidance-1; `guidance/ledger.py`). Scans EX-99.1 of 8-Ks with Item 2.02. Sentences with a forward verb and a value → metric (revenue, gross/operating margin, opex, total expenses, operating income, EPS, tax rate, capex, other income, share counts), basis (GAAP / non-GAAP / both / unspecified), period (sentence, else nearest outlook heading; comparison periods ignored), value (range, ± amount/%/bps, approximately, point) and stated prior guidance. Outlook tables read only under an outlook/guidance heading with one period; GAAP/non-GAAP columns from the header; unscaled money only for per-share rows or under "(in millions/billions)". Each ledger row stores the exact quote, its offsets, the period's source text, document sha256 and parser version. One `guidance_scan` row per release (parsed / none / review). Unparsed guidance-like sentences → review queue `guidance_unparsed`; same key with different values → `guidance_conflict`. Script: `scripts/run_guidance.py` (code only). Samples from 2026-10-08: Meta, NVIDIA, Amazon, Marvell, Intel, Micron, Infleqtion give numeric guidance in the release; Apple, Alphabet, Microsoft, Boeing do not.
- D-SRCH-12 (2026-10-08): Parser guidance-2 after the first live scan (53 releases: 31 parsed, 15 none, 7 review). Fixes: table cells are tabs in stored text; outlook tables need the outlook word in the header or the lead-in line just above (results tables were read as guidance); a forward verb must precede each value and the period is the one nearest before it (reported actuals in the same sentence were taken); capex aliases ("CapEx"); value-before-metric in spend phrasing; shared ± after "respectively"; footnotes no longer read as row values; noun cues ("projects", "than anticipated") and boilerplate dropped; a full-year period that ended before the release goes to review. Gaps found (call-only guidance, Tesla delivery KPIs) logged in DATA_SOURCES.md (DS1, DS2).
- D-SRCH-13 (2026-10-08): Parser guidance-3 after the second live scan (29 parsed, 21 none, 3 review). Negatives read ("$(0.14)", "($0.14)", "-$0.14", "(4.5)%"); a table row with an unread digit cell goes to review instead of guessing columns (Intel GAAP EPS losses had been replaced by the non-GAAP value); a bare point equal to a ± value's centre is consistent, not a conflict (NVIDIA tables); "guidance for/of" is a forward cue and net income a metric (Strategy); a sentence repeated in one release is queued once.
- D-SRCH-14 (2026-10-08): Third live scan (31 parsed, 20 none, 2 review). Owner challenged Intel's Q4 2025 GAAP tax-rate guidance of 476%: checked against intc.com (Q3 2025 release: outlook "Tax Rate 476% | 12%", reconciliation 476% − 464% = 12%) — transcribed correctly; Q1 2026 outlook (−79%, 11%, EPS $(0.21) / $0.00) and Q4 2025 EPS $(0.14) also match intc.com. Actual Q4 2025 GAAP tax rate was 198.5%: near-zero pretax income makes the ratio meaningless (failure mode below). Parser guidance-4: scale words read case-insensitively ("$40 Million").
- D-SRCH-15 (2026-10-08): Ratio guidance on a near-zero base is kept as stated but flagged `not_meaningful` with its reason (first rule: guided tax rate below 0% or above 50%). Flagged rows are shown with the reason and excluded from guidance-vs-actual scoring and LLM trend input; nothing is deleted (owner).
- D-SRCH-16 (2026-10-08): Model `gemini-3.1-flash-lite` to start ("Gemini 3.1 Flash" does not exist); billing enabled on the owner's key; LLM use minimized and gated behind an explicit owner request (owner).
- D-SRCH-17 (2026-10-08): Approved LLM use cases, each run only on owner request, input = passages selected by code, every claim quoted and verified (owner): (1) guidance change reasons (R19; code computes raised/lowered/narrowed, LLM quotes stated reasons) — built first to prove the call + verifier; (2) 10-K Item 1A year-over-year changes (code diffs paragraphs; needs prior-year 10-Ks); (3) milestones and challenger rungs with stated dates (R4, R21); (4) M02 theme naming and synonym proposals (phrases verified against EDGAR counts); (5) customer/supplier links (names verified in the quote). Never LLM: figures, Form 4 classification, technicals, scoring, unparsed guidance.
- D-SRCH-18 (2026-10-08): One LLM call per use case per company (or per filing pair); never bundled across use cases. Deliberate cross-company comparisons tag each passage with its company and the verifier rejects claims citing another company's passage. "Run all for this equity" makes separate calls in sequence. Runs start from a script now (token count + cost estimate, then y/n) and from per-section Analyze buttons in the UI later; the nightly job may suggest, never run. No free-form chat for now; grounded Q&A to be decided at the UI design (owner).
- D-SRCH-19 (2026-10-08): LLM layer built. `guidance/changes.py` (code): raised/lowered/narrowed/widened/reaffirmed per metric/basis/period between releases, or vs a prior stated in the same sentence; flagged rows skipped. `llm/provider.py`: google-genai `models.generate_content` with system instruction, temperature 0, JSON schema; settings and prices in `config/llm.toml`; key from `GEMINI_API_KEY`. `llm/verify.py`: quote must be in its passage (whitespace/quote/dash-normalized, ≥ 12 chars); every number in a claim must be in the cited quotes or the code-supplied facts (raw, millions or billions). `llm/runs.py`: identical requests served from storage at no cost; every call logged (`llm_call`); observations and citations stored; rejected ones kept with the reason and queued as `llm_rejected`. Use case 1 `llm/guidance_reasons.py` (prompt `prompts/guidance_reasons_1.md`): asks only about moved guidance, passages = the guidance sentence's passage and the next one in the announcing release; quotes from other releases rejected. Script `scripts/run_llm.py` (`--dry-run` shows the exact prompt, default asks y/N after a local cost estimate, `--rerun`).
- D-SRCH-20 (2026-10-08): First live call (Meta, gemini-3.1-flash-lite): 6 changes, 6/6 observations verified, 4,559 + 491 tokens, $0.0019; reasons matched their quotes (capex: component pricing and data-center costs; expenses: $2.4 billion legal charges; three correctly "no reason stated").
